**Dragging a tab (or anything else that moves the pointer a thousand times a second) is even on a fast screen** (`pacing.odin`, toolkit 0.34.0): every frame woken by input was shown at once, hundreds a second during a drag; they piled up in the swap chain, which showed them one per refresh, so the picture advanced a millisecond for three refreshes and then jumped (60 Hz window, tab dragged at 1 kHz: 440 frames made per second, 7 in 8 never shown, step error per refresh p95 18 px, 36 px at worst). Only the frame that starts an answer to input is shown at once now (`browser.frame.input_idle_periods`, 0 = the old behaviour); the others wait for the screen's slot, one per refresh (59 frames per second, all shown, step error p95 1 px). And a swap chain that was allowed two frames in flight for one input frame or one resize step kept two for good (the toolkit's latency object keeps a count when the latency is lowered again): fixed in the toolkit, the wait for the slot gates again. Measure with `tools\drag_fluidity.ps1`.
